## 11.1 What is Helm?

Helm is the **package manager for Kubernetes**. Instead of writing individual YAML files for every Kubernetes object, you use a Helm **chart** — a collection of templated YAML files with configurable values.

```
Without Helm:
  kubectl apply -f deployment.yaml
  kubectl apply -f service.yaml
  kubectl apply -f ingress.yaml
  kubectl apply -f configmap.yaml
  kubectl apply -f serviceaccount.yaml
  kubectl apply -f rolebinding.yaml
  ... for every app, every environment, manage separately

With Helm:
  helm install my-app my-chart --values prod-values.yaml
  helm upgrade my-app my-chart --values prod-values.yaml
  helm rollback my-app 1
  helm uninstall my-app
```

Helm also tracks **releases** — each install is a numbered release. You can rollback.

💡 **Interview**: *"What is Helm and why do you use it?"*  
→ "Helm is the package manager for Kubernetes. A Helm chart is a bundle of Kubernetes YAML templates with parameterized values. Instead of maintaining separate YAML files per environment, you maintain one chart and different values.yaml files (values-dev.yaml, values-prod.yaml). Helm tracks releases — each helm install or upgrade creates a numbered release stored as a Secret in the namespace. This enables `helm rollback` which re-applies the previous release's manifests. Helm also handles dependencies between charts."

## 11.2 Helm Chart Structure

```
my-chart/
├── Chart.yaml          # Metadata: name, version, description, dependencies
├── values.yaml         # Default values — everything is configurable here
├── charts/             # Dependency charts (sub-charts)
├── templates/          # Kubernetes YAML templates
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── ingress.yaml
│   ├── configmap.yaml
│   ├── _helpers.tpl    # Template helper functions (Go templates)
│   └── NOTES.txt       # Instructions shown after helm install
└── .helmignore
```

### A Template Example

```yaml
# templates/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ include "my-chart.fullname" . }}
  labels:
    {{- include "my-chart.labels" . | nindent 4 }}
spec:
  replicas: {{ .Values.replicaCount }}    ← from values.yaml
  template:
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        resources:
          {{- toYaml .Values.resources | nindent 12 }}
```

```yaml
# values.yaml (defaults)
replicaCount: 1
image:
  repository: nginx
  tag: stable
resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    cpu: 500m
    memory: 256Mi
```

```yaml
# values-prod.yaml (overrides)
replicaCount: 5
image:
  tag: 1.25.0-alpine    # pin to specific version in prod
resources:
  requests:
    cpu: 500m
    memory: 512Mi
  limits:
    cpu: 2000m
    memory: 1Gi
```

## 11.3 Essential Helm Commands

```bash
# Add a repository
helm repo add bitnami https://charts.bitnami.com/bitnami
helm repo update

# Search for charts
helm search repo nginx
helm search hub wordpress   # searches Artifact Hub

# Install a chart
helm install my-nginx bitnami/nginx \
  --namespace web \
  --create-namespace \
  --set replicaCount=3 \
  --set service.type=ClusterIP

# Install with values file
helm install my-nginx bitnami/nginx \
  --namespace web \
  --values my-nginx-values.yaml

# List releases
helm list -A   # all namespaces

# Get status of a release
helm status my-nginx -n web

# See what Helm would deploy (dry-run)
helm install my-nginx bitnami/nginx --dry-run --debug

# Upgrade a release
helm upgrade my-nginx bitnami/nginx \
  --namespace web \
  --reuse-values \
  --set replicaCount=5

# Rollback to previous release
helm rollback my-nginx 1 -n web   # rollback to revision 1

# See release history
helm history my-nginx -n web

# Get rendered templates (debug)
helm get manifest my-nginx -n web

# Get values used in a release
helm get values my-nginx -n web

# Uninstall
helm uninstall my-nginx -n web
```

## 11.4 Deploy a Real Application Stack

Let's deploy a full WordPress + MySQL stack as a practical exercise:

```bash
# [M1]
kubectl create namespace wordpress

# Install MySQL as StatefulSet
helm install mysql bitnami/mysql \
  --namespace wordpress \
  --set auth.rootPassword=mysecretpassword \
  --set auth.database=wordpress \
  --set auth.username=wordpress \
  --set auth.password=wordpresspassword \
  --set primary.persistence.storageClass=longhorn \
  --set primary.persistence.size=10Gi

# Watch MySQL come up
kubectl get pods -n wordpress -w
# mysql-0 should reach Running

# Install WordPress
helm install wordpress bitnami/wordpress \
  --namespace wordpress \
  --set wordpressUsername=admin \
  --set wordpressPassword=adminpassword \
  --set mariadb.enabled=false \
  --set externalDatabase.host=mysql.wordpress.svc.cluster.local \
  --set externalDatabase.user=wordpress \
  --set externalDatabase.password=wordpresspassword \
  --set externalDatabase.database=wordpress \
  --set persistence.storageClass=longhorn \
  --set service.type=ClusterIP \
  --set ingress.enabled=true \
  --set ingress.hostname=wordpress.yourdomain.com

# Check everything
kubectl get all -n wordpress
```

## 11.5 Resource Requests and Limits

**Requests** = What the scheduler uses to decide where to place the pod.  
**Limits** = The max the container can use (enforced by cgroups).

```yaml
resources:
  requests:
    cpu: "250m"       # 0.25 cores — scheduler reserves this
    memory: "256Mi"   # scheduler reserves this
  limits:
    cpu: "1000m"      # 1 core max — container throttled if exceeded
    memory: "512Mi"   # container KILLED if exceeded (OOMKilled)
```

🔍 **CPU throttling vs memory OOMKill:**
- **CPU over limit**: Container is throttled (slowed down, not killed). The cgroup CPU scheduler limits it.
- **Memory over limit**: Container is immediately OOMKilled. There's no graceful degradation for memory.

💡 **Interview**: *"What happens when a pod exceeds its memory limit?"*  
→ "The container is OOMKilled (Out of Memory Killed) by the kernel's OOM killer. The container restarts with backoff (if RestartPolicy is Always, which is the default). The event will show as `OOMKilled` in `kubectl describe pod`. It's worth knowing that there's a difference between request and limit: the request is what the scheduler sees for placement decisions, while the limit is the cgroup enforcement. A pod can use more memory than its request (if the node has slack) but can never exceed its limit."

### Quality of Service Classes

Kubernetes assigns QoS class based on resource configuration:

| QoS Class | Condition | Eviction Priority |
|-----------|-----------|------------------|
| `Guaranteed` | requests == limits for all containers | Last evicted |
| `Burstable` | requests < limits, or only one set | Middle |
| `BestEffort` | No requests or limits at all | First evicted |

```bash
# [M1] — check pod QoS class
kubectl get pod my-pod -o jsonpath='{.status.qosClass}'
```

When a node is under memory pressure, kubelet evicts `BestEffort` pods first, then `Burstable`, keeping `Guaranteed` pods running.

## 11.6 Horizontal Pod Autoscaler (HPA)

```bash
# [M1] — HPA requires metrics-server (pre-installed with RKE2)
kubectl top pods   # verify metrics-server is working

# Deploy a scalable app
kubectl create deployment hpa-test --image=nginx --port=80
kubectl expose deployment hpa-test --port=80

# Create HPA (scale between 2-10 pods based on CPU)
cat << 'EOF' | kubectl apply -f -
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hpa-test
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hpa-test
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50   # scale up when avg CPU > 50%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60   # wait 60s before scaling up again
    scaleDown:
      stabilizationWindowSeconds: 300  # wait 5 min before scaling down
EOF

kubectl get hpa hpa-test -w
# Shows: TARGETS, MINPODS, MAXPODS, REPLICAS
```

## 11.7 DaemonSets

A DaemonSet ensures exactly **one pod runs on every node** (or matching nodes).  
Used for: log collectors, monitoring agents, CNI plugins, node-local caches.

```bash
# [M1] — example: deploy a log collector on all workers
cat << 'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: log-collector
spec:
  selector:
    matchLabels:
      app: log-collector
  template:
    metadata:
      labels:
        app: log-collector
    spec:
      # Only run on workers (tolerate nothing on masters)
      nodeSelector:
        role: worker
      containers:
      - name: collector
        image: fluent/fluent-bit:latest
        volumeMounts:
        - name: varlog
          mountPath: /var/log
          readOnly: true
      volumes:
      - name: varlog
        hostPath:
          path: /var/log
          type: Directory
EOF

kubectl get daemonset log-collector
# DESIRED=3, CURRENT=3, READY=3 (one per worker)
```

## 11.8 Namespace Strategy

Good namespace design prevents chaos:

```bash
# Recommended namespaces
kubectl create namespace production       # prod workloads
kubectl create namespace staging          # staging workloads
kubectl create namespace monitoring       # Prometheus, Grafana
kubectl create namespace logging          # log infrastructure
kubectl create namespace security         # Vault, OPA, etc.

# Apply ResourceQuota per namespace (prevent any single namespace from using all resources)
cat << 'EOF' | kubectl apply -f -
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"        # total CPU requests in this namespace
    requests.memory: 40Gi     # total memory requests
    limits.cpu: "40"          # total CPU limits
    limits.memory: 80Gi
    pods: "200"               # max pods
    services: "50"
    persistentvolumeclaims: "30"
EOF

# Apply LimitRange (default resources if pod doesn't specify)
cat << 'EOF' | kubectl apply -f -
apiVersion: v1
kind: LimitRange
metadata:
  name: production-limits
  namespace: production
spec:
  limits:
  - default:          # default limit if not specified
      cpu: "500m"
      memory: "256Mi"
    defaultRequest:   # default request if not specified
      cpu: "100m"
      memory: "128Mi"
    type: Container
EOF
```
